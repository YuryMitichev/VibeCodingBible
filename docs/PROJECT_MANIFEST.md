# PROJECT MANIFEST

Version: 0.2.0

Status: Active

---

# 1. Mission

**Vibe Coding Bible** — это долгосрочный инженерный проект, цель которого заключается в создании наиболее полного практического руководства по современной AI-assisted разработке программного обеспечения.

Репозиторий является первичным источником знаний.

Из него в дальнейшем могут быть автоматически сформированы:

- PDF
- EPUB
- DOCX
- HTML-сайт
- документация
- обучающий курс
- база знаний
- презентации
- справочник

Книга не должна зависеть от конкретной модели ИИ или одного инструмента. Все рекомендации должны строиться вокруг принципов, которые сохраняют актуальность по мере развития технологий.

---

# 2. Vision

Проект должен стать:

- инженерным справочником;
- практическим учебником;
- системой знаний;
- рабочим пособием;
- источником шаблонов;
- коллекцией лучших практик;
- живой документацией по AI-assisted разработке.

Главная цель — научить читателя проектировать, создавать, сопровождать и развивать программные продукты совместно с искусственным интеллектом.

---

# 3. Project Principles

## 3.1. Практика важнее теории

Каждая концепция должна сопровождаться примером применения.

## 3.2. Объяснение важнее определения

Недостаточно дать определение термину. Необходимо объяснить:

- что это;
- зачем это;
- когда применять;
- когда не применять;
- типичные ошибки.

## 3.3. Независимость от инструментов

Книга не должна превращаться в инструкцию по одному сервису.

Инструменты используются только как примеры реализации общих принципов.

## 3.4. Эволюционность

Материал должен быть организован так, чтобы его можно было обновлять без полной переработки книги.

---

# 4. Target Audience

Книга рассчитана на несколько уровней подготовки.

## Beginner

Человек никогда не использовал AI для разработки.

Цель:

показать основы.

---

## Intermediate

Использует ChatGPT или Cursor.

Цель:

научить строить полноценный процесс разработки.

---

## Advanced

Создает большие проекты.

Цель:

показать архитектурные подходы, масштабирование, автоматизацию и организацию командной работы.

---

## Expert

Архитекторы, технические руководители, основатели продуктов.

Цель:

научить проектировать AI-first процессы разработки.

---

# 5. Scope

Проект включает:

- разработку ПО;
- управление требованиями;
- проектирование архитектуры;
- работу с AI;
- автоматизацию;
- тестирование;
- сопровождение;
- документирование;
- командную работу;
- лучшие инженерные практики.

Проект не является:

- справочником по языку программирования;
- учебником по математике;
- документацией одного инструмента.

---

# 6. Repository Structure

Репозиторий организован как knowledge monorepo.

Основные каталоги:

- docs/
- book/
- templates/
- prompts/
- playbooks/
- patterns/
- examples/
- diagrams/
- scripts/
- build/

Каждый каталог имеет одну четкую ответственность.

---

# 7. Source of Truth

Единственным источником истины является Git-репозиторий.

Все изменения проходят через систему контроля версий.

Документы вне репозитория считаются временными черновиками.

---

# 8. Writing Standards

Каждая глава должна содержать:

1. цель главы;
2. проблему;
3. объяснение;
4. пример;
5. антипример (если уместно);
6. практическое применение;
7. рекомендации;
8. вывод;
9. ссылки на связанные главы.

---

# 9. Quality Standards

Материал считается готовым только если:

- отсутствуют внутренние противоречия;
- используется единая терминология;
- примеры воспроизводимы;
- структура логична;
- материал понятен без обращения к будущим главам;
- соблюден стиль книги.

---

# 10. Versioning

Используется семантическое версионирование.

Пример:

0.1.0 — Bootstrap

0.2.0 — Foundation

0.3.0 — Outline

0.5.0 — First Draft

0.8.0 — Technical Review

1.0.0 — First Public Release

---

# 11. Git Workflow

Каждый логически завершенный результат оформляется отдельным коммитом.

Сообщения коммитов должны быть понятными и отражать суть изменений.

Примеры:

- feat(book): add chapter 01
- docs(style): refine writing guide
- refactor(outline): restructure part II
- fix(diagrams): correct architecture diagram

---

# 12. Definition of Done

Документ считается завершенным, если:

- достигнута поставленная цель;
- проведена редактура;
- отсутствуют известные логические ошибки;
- соблюдены требования проекта;
- документ готов к использованию без дополнительных пояснений.

---

# 13. Change Policy

Изменения в фундаментальных документах (Manifest, AI Context, Style Guide) допускаются только при наличии веской причины.

Любое изменение должно быть осознанным и не нарушать согласованность проекта.

---

# 14. Long-Term Maintenance

Проект рассматривается как долгосрочный.

Приоритеты:

1. качество;
2. согласованность;
3. практическая ценность;
4. актуальность;
5. расширяемость.

---

# 15. Roles

## Project Owner

Определяет стратегическое направление проекта и утверждает ключевые решения.

## Architect

Проектирует структуру книги, репозитория и взаимосвязь материалов.

## Technical Editor

Следит за единообразием терминологии, структуры и качества текста.

## Contributors (в будущем)

Предлагают изменения через отдельные коммиты или pull request, соблюдая правила проекта.

---

# 16. Success Criteria

Проект можно считать успешным, если он:

- помогает читателям эффективно работать с ИИ при разработке;
- остается актуальным при появлении новых моделей и инструментов;
- имеет понятную структуру и единый стиль;
- может служить основой для книги, сайта, курса и базы знаний без переписывания исходных материалов.
