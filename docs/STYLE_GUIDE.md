# STYLE GUIDE

Version: 0.2.0

Status: Active

---

# 1. Назначение

Этот документ определяет единый стиль книги **Vibe Coding Bible**.

Все главы, приложения, шаблоны и дополнительные материалы должны соответствовать данным правилам.

Основная цель — сделать книгу цельной, последовательной и удобной для чтения независимо от того, когда и кем была написана конкретная глава.

---

# 2. Основные принципы

Приоритеты располагаются в следующем порядке:

1. Ясность.
2. Практическая ценность.
3. Логичность.
4. Последовательность.
5. Полнота.
6. Краткость.

Если приходится выбирать между краткостью и понятностью — выбирается понятность.

---

# 3. Тон повествования

Книга пишется спокойным инженерным языком.

Текст должен:

- объяснять;
- обучать;
- помогать принимать решения.

Текст не должен:

- продавать идеи;
- рекламировать инструменты;
- преувеличивать возможности ИИ;
- использовать кликбейт.

---

# 4. Обращение к читателю

Используется уважительное обращение на «вы».

Пример:

> Рассмотрим, как этот подход работает на практике.

Избегать:

> Сейчас мы с вами...

---

# 5. Структура главы

Каждая глава должна содержать следующие разделы:

1. Цель главы.
2. Зачем это важно.
3. Проблема.
4. Основная теория.
5. Практический пример.
6. Работа с ИИ.
7. Типичные ошибки.
8. Лучшие практики.
9. Чек-лист.
10. Итоги.
11. Что изучить дальше.

Допускается добавление подразделов, если это улучшает восприятие.

---

# 6. Размер материалов

Рекомендуемый объем:

- глава — 3 000–8 000 слов;
- раздел — 500–1 500 слов;
- пример — до 100 строк кода;
- таблица — до 10–15 строк.

Если тема требует большего объема, лучше разделить материал на несколько глав.

---

# 7. Примеры

Каждая новая концепция должна сопровождаться примером.

Желательно использовать реальные сценарии:

- CRM;
- интернет-магазин;
- Telegram-бот;
- REST API;
- SaaS;
- CLI;
- AI-агент.

Пример должен быть законченным и понятным без обращения к внешним источникам.

---

# 8. Код

Код используется только тогда, когда он помогает понять идею.

Код должен быть:

- минимальным;
- читаемым;
- самодостаточным;
- снабжен кратким пояснением.

Не следует приводить большие фрагменты кода без необходимости.

---

# 9. Диаграммы

Используются для объяснения структуры и процессов.

Предпочтительные форматы:

- Mermaid;
- C4;
- Sequence Diagram;
- Flowchart;
- ERD;
- State Diagram.

Каждая диаграмма должна сопровождаться текстовым объяснением.

---

# 10. Таблицы

Таблицы используются для сравнения, а не для хранения большого объема информации.

Если таблица становится слишком большой, ее следует заменить несколькими таблицами или списками.

---

# 11. Списки

Используйте маркированные списки для перечислений и нумерованные — для последовательностей действий.

Не создавайте списки из одного элемента.

---

# 12. Терминология

Каждый новый термин:

- вводится один раз;
- определяется;
- далее используется последовательно.

Не допускается использование разных терминов для одного и того же понятия без объяснения.

---

# 13. Аналогии

Аналогии допустимы, если они действительно помогают понять материал.

Избегать чрезмерного количества метафор и сравнений.

---

# 14. Истории и кейсы

Истории должны быть основаны на реальных инженерных ситуациях или правдоподобных сценариях.

Каждый кейс должен отвечать на вопрос:

> Почему выбран именно такой подход?

---

# 15. Практические задания

По возможности каждая глава завершается небольшим заданием.

Задание должно позволять закрепить изученный материал на практике.

---

# 16. Чек-листы

Если тема предполагает повторяемый процесс, глава должна содержать чек-лист.

Чек-лист должен быть коротким и пригодным для использования в реальной работе.

---

# 17. Ссылки между главами

Если тема подробно раскрывается в другой главе, необходимо добавить ссылку на нее.

Это помогает читателю строить целостную картину.

---

# 18. Редакционные запреты

Не использовать:

- необоснованные утверждения;
- чрезмерный энтузиазм;
- жаргон без объяснения;
- длинные вводные фразы;
- повторение одной мысли разными словами.

---

# 19. Definition of Done для главы

Глава считается готовой, если:

- цель достигнута;
- теория объяснена;
- приведен практический пример;
- добавлены рекомендации по работе с ИИ;
- перечислены типичные ошибки;
- есть чек-лист;
- есть выводы;
- соблюден единый стиль книги.

---

# 20. Принцип постоянного улучшения

Документы и главы могут дополняться и улучшаться, но каждое изменение должно:

- повышать качество материала;
- сохранять согласованность с остальной книгой;
- не нарушать ранее принятые правила проекта.
